What changed

Two Phase 3 implementer agents merged into one

Problem

Phase 3 shipped two implementer agent types that did the same job. One took an execution wave, the other took a single module while sibling agents built other modules in the same working tree. Choosing between them was a judgement call at every dispatch, and there was no rule that made the choice obvious.

Root cause

The two prompts were split by WHICH AGENT carried a rule instead of by WHEN the rule applies. Almost everything in them was the same job described twice, so the pair drifted: the module prompt carried a build-order rule and a private-database rule the wave prompt never received, and neither file knew it.

Solution

There is one agent type now, hackify:implementer, and the input sibling_tracks is the mode switch. Pass none and it works alone, which covers the solo foundation wave, the solo assembly wave and any round holding a single track. Pass the other tracks' names and it also reads a new rules file and applies every rule in it on top: its own private test database, cross-module type errors that are expected and not its to fix, reporting shared-code defects instead of fixing them, building against the plan's interface rather than against code a sibling has not landed, a ban on git checkout, restore and stash while a sibling has uncommitted work in the same tree, and the eight-item handoff the assembly wave mounts from. Those rules live in their own file rather than in the prompt because both contracts in one file came to 887 lines against a hard 500-line cap, and splitting on when a rule applies keeps a solo dispatch from paying for machinery that protects nothing. Nine of the 21 inputs now accept the literal none, so quick mode can dispatch the same agent without inventing values it has no use for.
