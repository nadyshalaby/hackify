Scope Phase 3's one-agent-per-wave rule so independent waves can run together

2026-08-26-phase-3-parallel-waves · generated 2026-08-26

Sprint goal. Phase 3 stops being the workflow's throughput floor. One agent still takes a wave whose tasks share a read surface, but waves that share nothing may run at the same time, and every safety property the old rule carried survives the change.

What changed & why it matters

Building a feature used to run one worker at a time, even when the pieces of work had nothing to do with each other. Now the workflow checks three things before it decides: do any two pieces touch the same file, does one read something the other is rewriting, and do they both need the same single resource. If all three come back clean, the pieces run at the same time. If any one of them does not, one worker takes the whole batch, exactly as before. Nothing about safety was traded for the speed: no permission list was widened, no phase moved, and the rule that stops everything at the first failure is untouched. Two other things changed alongside it. The review step now runs once instead of looping, so a task finishes in predictable time rather than however long the findings keep coming, and the review panel no longer skips checkers based on what the change looked like, so four reviewers read every non-trivial change instead of one plus whatever got through. And the questions asked at the very start of a task were rewritten to be about the real business you are in rather than a generic app.

What changed

Independent waves may now run at the same time

Problem

Phase 3 dispatched one agent per wave unconditionally, while the reason it gave for doing so, that a wave's tasks read the same code, is conditional. Work in separate modules that imported nothing from each other still ran one at a time.

Root cause

The rule was written unconditionally at every site that stated it, and a separate sentence about phase ordering, parallelism lives inside a phase never across phases, was read as forbidding concurrent waves too.

Solution

A three-condition partition test, written once and pointed at from every other site: no file in more than one subset, no read or write edge between subsets in either direction, and no shared serial resource. All three hold and the subsets may go out together, one agent each; any one fails and one agent takes the whole wave.

Verification evidence

Validator ALL CHECKS PASSED at 1417 ok lines against a floor of 1350; tamper battery 148 passed; ban tokens 155 passed; mirrors 9 of 9.

Phase 5 closes once instead of looping

Problem

The review phase kept scanning and fixing until a round came back clean, so a task's finishing time depended on how long findings kept arriving.

Root cause

The exit condition was a settled diff, which is a property of the work rather than a bound on the process.

Solution

One reviewer panel, one refuter, then the surviving findings are fixed and the phase ends. A defect a fix introduces is fixed in the same sequence and reported, never by opening a new round. The panel is also no longer gated, so four lenses read every non-trivial change.

Verification evidence

The un-gated panel filed 41 findings where the gated rounds averaged 15. Check [75f] was re-aimed at the no-second-panel clause and proven to red when that clause is softened.

Deployment status

Committed on the branch. Not merged or tagged.

Waves declare what they deleted

Problem

A deleted file reached the parent as a path in the round's diff that no wave claimed, which looks exactly like the stray edit the reconciliation exists to catch, so every deletion had to be reported as a failure.

Root cause

The wave's declaration covered only what it wrote. Two fixes from the same review round then collided: one hardened deletions on the ground that no declaration could carry one, and the other added the declaration.

Solution

Deletions get their own fence in the wave's report, bound by the same file allowlist, and the parent reconciles against it. Attribution now comes from the wave's own declaration, which is authorship, rather than from allowlist membership, which never was.

Verification evidence

Five rows against the document's own runnable block: a declared deletion inside the allowlist reconciles, one outside fails, an undeclared vanished path still fails and names the allowlists that held it, a path declared twice fails, and a missing fence file fails rather than being skipped.

What you install is compared against what it was built from

Problem

The built trees under dist/ are what a user actually installs, and nothing compared them against the source they were copied from. A source file could be edited and the shipped copy left stale.

Root cause

dist/ is ignored by git wholesale, so no diff and no review ever saw it.

Solution

A new integrity check hashes every shipped file against its canonical source and reports both the files that differ and the files the sync plans but never writes. CI now builds dist/ before running the validator, so the check actually fires there.

Verification evidence

It found 192 differing files and 6 planned-but-unwritten out of 791 on its first real run, all repaired by a resync. Eleven tamper rows cover every branch, including the skip branch that had printed green for its whole life.

Deployment status

Committed on the branch. Not merged or tagged.

The opening questions are about your business, not a generic app

Problem

The clarify questions treated every task as a simple app and drifted away from what the work actually had to deliver.

Root cause

The seven question banks were written generically, with no shared source of domain facts to cite.

Solution

All seven banks rewritten with market-standard flows, plus a new shared file of domain mechanisms covering twelve domains. Recommendations must now name a mechanism and the failure it prevents; company names, best practice, industry standard and invented numbers are banned as bare assertions.

Verification evidence

Question banks 7 checked with 0 defects; the clarity checker and the ban-token suite both cover the new file.
