What changed

Groom routing: one phrase meant two opposite things

Problem

Groom is the skill you use to talk an idea through before any building starts. Saying 'ship it' to it meant 'stop talking, start building'. But that same phrase, appearing in your message, told the next stage to recommend the riskiest way of delivering the work: merged straight into the main branch with nobody reviewing it. Groom hands off in the same turn, so the message that meant 'let's begin' was still the one being read when that recommendation was made. Two smaller problems sat beside it. Groom's list of phrases that start it and its list of words that stop it contradicted each other, with nothing saying which won. And the list in its documentation claimed to be complete while missing three entries.

Root cause

The two lists were written at different times and neither knew about the other. The 'ship it' collision is the same kind of thing one step further out: two separate files each picked a sensible meaning for a common phrase, and nobody checked whether they were the same meaning.

Solution

'ship it' is no longer a phrase that starts building, and the reason sits beside the list so it does not get added back. The precedence between the two lists is now written down, matching what the existing tests already assumed. The missing three entries were added, and a new check makes sure that list and the routing list cannot drift apart again.

Verification evidence

The new check was watched failing before it was trusted. Its first version had the same disease it was meant to cure: it could not fail on one of its eight phrases, because a sentence elsewhere in the file happened to quote that phrase and the check read the whole page. I found that by deleting the entry and watching it pass anyway. It now reads the list itself and fails on exactly that case.

Agent prompts had drifted from the rules they quote

Problem

The plugin runs work through specialised agents, each with a written prompt telling it how to be rigorous. Five of those prompts had quietly stopped matching the rules they cite. The worst: the agent whose whole job is to judge whether a reported problem is real could dismiss one for free, just by saying it could not restate the claim clearly, which is uncertainty rather than evidence. Its own next paragraph says to keep anything ambiguous. Also: the quality reviewer could report the size limits as checked when it had been handed an empty table; a rule listing eight kinds of file was quoted as three in twelve places; the design reviewer with no spec skipped six of its nine steps including colour contrast; and three agents had no way to refuse a broken instruction at all.

Root cause

Nothing compared these prompts against the rules they quote. Every one was correct when written. The rules moved, or a prompt was edited in one place and not the matching one, and there was no check that would notice. Three of the five had contradictions sitting a few lines apart in the same file.

Solution

All five fixed, plus two more found while fixing them. The refuter now records an unclear finding as needing restatement, which closes nothing and keeps it in the queue, and a second free-dismissal path was closed alongside it. The eight file kinds are now correct everywhere and a new check reads them from the rules file itself at run time, so the rule and its guard cannot drift apart. The design reviewer runs everything that does not genuinely need a project spec. The three agents without a refusal gate have one, each traced by hand.

Verification evidence

Both new checks were watched failing on real breakage before being trusted, and I reproduced both myself rather than taking the reports on faith. The full gate passes twice with zero failures and 1388 passing lines, all 18 test suites pass, and every file stays inside the 500-line limit, including two that had three and seven lines spare and had to buy room back by rewording rather than dropping anything.
