# Hackify Quick (The Default Compressed Flow)

**This is where a substantive prompt lands.** Same end-to-end discipline as the main hackify skill (clarify → implement → verify → summary), ceremony stripped. Nothing about the ask routes it elsewhere: not the file count, not a cross-file refactor, not a redesign, not an unknown root cause, not auth or crypto or a migration or a secret. Full hackify is a mode the user asks for by name, and until they do the work happens here. Self-contained under the same **three-tier skill-call rule** as full hackify (`../hackify/SKILL.md`): runtime-native skills mapped in `runtime-adapters.md` are allowed, plugin-bundled siblings are allowed, third-party plugin skills are never invoked. Running a bundled plugin script by path (the law-scout) is not a skill call at all. Explicit user-initiated promotion re-enters full hackify by name. The ceremony that mode adds costs roughly three times the tokens and wall-clock, which is exactly why it is opt-in.

All three orchestration defaults apply ([`../hackify/references/orchestration.md`](../hackify/references/orchestration.md)). Quick mode fans out on the implement side as wide as the partition asks for, up to the concurrent-wave budget, and fans out on the review side too: the five-agent panel by default, plus one refuter whatever the width; ask for the merged reviewer by name and the review side collapses to one reviewer, still with its one refuter; announce the tier in the Phase 1 goal-anchor line and honor `light mode` / `no ultracode` / `cheap mode` / `single agent`. The iteration driver still carries the task across turns until the ledger is ticked, quick has no work-doc, so its exit condition is the session-local ledger, not an archived doc. The completion sentinel applies here too: print the paste-ready `/goal <condition>` line beside the Phase 1 goal-anchor line, naming the commit plus the green triad and a closed review round. Quick tasks usually finish in one turn and the line still earns its place, the moment a "quick" fix turns out not to be quick, the condition is already written. You print it, only the user sets it, and never from a subagent.

The always-on ship bar applies here in full, and it stays cheap on small diffs by design: the ship gate legs are blocking only when the diff touched something the build or startup path consumes, so a typo fix records three `⏭ skipped` rows instead of booting the app (`../hackify/references/ship-gate.md`).

## Workflow shape

```
Phase 1 (clarify + goal anchor) → Phase 3 (implement) → Phase 4 (verify) → Phase 5-lite (five-agent panel, every lens) → Phase 6 (Step C.5 cleanup + Step F update log)
```

No Plan+Gate. No Spec self-review. The five-agent panel (A, B, D, F unconditionally, E on a UI-bearing diff), plus one refuter over every finding in the round, runs the address-all review by default; ask for the merged reviewer by name and it runs alone instead. No four-options finish menu. The update log is the mandatory artifact, and the page quick publishes is an extra on top of it that never gates anything (`skills/hackify/references/work-doc-artifact.md`).

**The `lite` in `5-lite` names the phases around the review, never the review itself.** Full mode dispatches the same five-agent panel, the same one refuter behind it, and the same one-round address-all loop, so the two modes review a diff identically. What quick drops sits on either side of that step: the written plan the review would otherwise be measured against, and the four-options finish menu after it.

## Phase ledger, trackable, ordered (always-on)

Open a **phase ledger** at task start, one item per kept phase. Clarify → Implement → Verify → Review-lite → Cleanup → Summary. Rules (full contract: `../hackify/references/phase-ledger.md`):

- **Substrate.** The runtime's **todo tracker** primitive when the session actually exposes one, otherwise a printed markdown checklist in chat, re-printed at **every** phase boundary. **On Claude Code the printed block is the normal path**, not an exotic edge case, because the todo tracker is frequently absent from the session tool surface. Quick keeps nothing on disk by contract, so that printed block is the ONLY record its ledger has, which makes the re-print rule load-bearing rather than cosmetic. The ledger degrades to visible-but-not-interactive, never to absent. On the fallback a tick is an edit plus a re-print: `- [ ]` open, `- [>]` the single in-progress item, `- [x]` done.
- **The republish rides the tick.** The run's page exists from Phase 1 on (see the Phase 1 row above), so a tick is: print the block, then republish the page. It is not a separate step, it does not open a new turn, and the user's one link stays current without anyone re-printing it. Contract, the degrade path included: `../hackify/references/work-doc-artifact.md`.
- One item `in_progress` at a time. No later phase starts until the current phase's exit artifact exists and its item is `completed`.
- **No step is ever silently dropped.** Quick is short by design, and short is not the same as silent. Every one of quick's own items ends either `completed`, or `completed` with a one-line reason written into the printed block, e.g. `Phase 1, skipped: zero ambiguity, the ask names the file and the line`. Never delete an item to make progress look done, and never let one disappear because the turn ran long.
- **Reflect after each item**, one line: what changed, did it pass, what is next, then advance.
- Quick keeps no work-doc and no archive item, so the ledger is session-local. It exists to force order and reflection, not to survive a restart.

## Expert mindset (always-on)

Even in quick mode, think as a **senior, multi-disciplinary engineer**, problem-solver, security, performance, architect, advisor, verifier. The asks that look smallest are where broken work hides, and quick mode now carries the ones that do not look small either. Prove instead of claim; when unsure, ask. Doctrine: `../hackify/references/expert-mindset.md` (a tight version is injected every prompt from `rules/expert-mindset.md`, beside the always-on `rules/hard-caps.md`, `rules/perf-guardrails.md`, `rules/phase-discipline.md` and `rules/claim-integrity.md`, five injected files in all, so the caps, the performance law and the no-silent-drop phase law all bind in quick mode too).

## Phase 3b, the root-cause hunt (kept in full, never skipped)

**A debug ask stays in quick mode like every other ask; needing a root cause is not a routing signal.** Quick owns debug asks outright, so it runs full mode's 4-phase hunt in place rather than promoting for it. The protocol is `../hackify/references/debug-when-stuck.md`, taken in full and unchanged: D1 root-cause investigation before any fix, D2 pattern analysis against a working sibling, D3 one written hypothesis at a time, D4 the fix applied at the source with its regression test. Read that file when the hunt fires. Do not restate it here, and do not run a shortened version of it because the ask arrived in quick mode.

**The trigger conditions are that file's, unchanged**: two honest failed fix attempts on the same unit, an error message that contradicts what the ask predicted, an unrelated test failing after the change, or a reproduction that is not deterministic. **Always find root cause before attempting fixes. Symptom fixes are failure.** A third blind fix after two misses is the exact move the protocol exists to stop.

**The circuit breaker is explicit and it binds here.** If 3 hypotheses fail, STOP and surface to the user. Do not attempt fix #4. Three disproved hypotheses in a row is a signal about the design rather than an invitation to guess again, so write the halt as one paragraph: what you tried, what you learned, and what you now suspect the architectural problem is.

**One adaptation, stated rather than papered over.** `debug-when-stuck.md` writes its hypotheses, its halt and its `status: debugging` into the work-doc, and quick keeps no work-doc. Here those go to chat, in the reflection line of the printed phase ledger, so the hunt still leaves a visible record for as long as the session lasts. Nothing else about the protocol changes. That the record dies with the session is one more thing full mode buys, and the user reaches it by name like everything else.

## Asking for the merged reviewer

**The merged all-lens reviewer stays registered, and you reach it by asking, in whichever mode you are in.** Say "use the merged reviewer" or "single reviewer round" on this diff and the parent dispatches `hackify:reviewer` alone exactly as `../hackify/references/phases/phase-5-review.md` describes, then the same refuter behind it and the same one-round cap. No promotion is needed, and none is implied: full mode routes to the five-agent panel too, so the merged reviewer is a request rather than a mode.

**It is your request and never the parent's judgment call.** Nothing about a diff, its size, its file count, the surface it touches or how sensitive it looks, asks for the merged reviewer on your behalf. The trap table below already rules out reading a diff's shape as an implied request, and that stays true here.

## Promotion to full hackify (user-initiated only)

Quick mode never auto-promotes. The user explicitly triggers promotion by saying any of these phrases (case-insensitive, scanned in the most recent user message only):

- `switch to full` / `switch to full mode`
- `go to full mode` / `go to full hackify`
- `promote to full` / `promote this to full`
- `/hackify:hackify` (slash command)
- `do full review` / `run Phase 5` / `run multi-reviewer` (an explicit request for full mode's whole ceremony, so it promotes; wanting only the merged reviewer on this diff needs no promotion, see **Asking for the merged reviewer**)

No diff-size, file-count, attempt-counter, or path-pattern check ever auto-promotes. If the user is silent, quick mode stays in quick mode for the whole task, even if the diff grows large or touches sensitive paths. That is the user's stated preference.

## Promotion procedure

On user-initiated promotion: (1) STOP implementation; (2) write a work-doc from accumulated context at `<project>/docs/work/<YYYY-MM-DD>-<slug>.md` (template at `skills/hackify/references/work-doc-template.md`); (3) re-enter full hackify Phase 2 (Plan+Gate); (4) preserve intent + clarify-answers + any partial diff in the Daily Updates section. Set frontmatter `current_task: (promoted from quick mode, awaiting gate)`. Do not silently re-dispatch implementation agents.

## There is no shape that routes away from quick mode

**Quick mode has no non-trigger list, and nothing about the ask sends the work to full hackify.** File count, cross-file refactors, redesigns, an unknown root cause, auth, crypto, migrations, secrets, tokens, passwords, none of it routes. The one and only way full mode runs is the user asking for it, in one of the promotion phrases listed above, and reading a shape as an implied request is the mistake this section exists to stop.

That is a decision the user made with the tradeoff in front of them. A sensitive diff gets the five-agent panel by default, here and in full mode alike, same as any other diff; nothing about its surface reaches for the merged reviewer on the user's behalf. Do not reintroduce a carve-out because a particular diff feels like it deserves one.

## Update log (mandatory)

End every task with a plain-language **update log**: one block per change, five fields each, in this order.

```
**Problem**
**Root cause**
**Solution**
**Verification evidence**
**Deployment status**
```

Separate blocks with a line containing exactly `----`. Quick mode typically produces one block; up to three if the fix touched separate things.

Write it the way you would explain the work out loud: everyday words, no jargon the user did not use, and never a phase number, task ID, reviewer letter or scout name. Field-by-field guidance, voice rules, and a worked example: `skills/hackify/references/finish.md` Step F.

Print to chat. If the user promoted to full hackify mid-task, append the log to the new work-doc's Retrospective under `## Update log`. For on-demand invocation, see `commands/summary.md` (`/hackify:summary`).

**Then write the log into the run's page and republish that page one last time.** The update log is the page's last block. The page has existed since Phase 1 and has been republished on every ledger tick since, so this final republish leaves the user's one link showing the finished run rather than minting anything new. That is the whole of what is quick-specific here. Every rule the page runs on, the four blocks, the temp-directory rule, the one-link contract and what to say where the runtime cannot publish, is `skills/hackify/references/work-doc-artifact.md` under `## Quick mode`, and it is stated there once so this file cannot drift away from it.

## Anti-rationalizations (STOP and apply the listed reality)

| Thought | Reality |
|---|---|
| "I can skip Phase 4 verify, it is just a typo" | Phase 4 stays. Typo fixes still need lint + typecheck to pass. The verification triad is the cheapest insurance in the workflow. |
| "User said 'quick' so we skip Phase 1 clarify" | Only skip clarify if there is zero ambiguity in the ask. If even one detail is unclear, run the wizard, one batched question is cheaper than a wrong implementation. |
| "An update log is overkill for a one-line fix" | It's mandatory. One block is fine. The user always knows what landed and why. |
| "I'll fold verify and review into one step" | The ledger keeps them separate and ordered. Tick Verify `completed` before Review-lite starts. |
| "This step obviously does not apply here, no need to mention it" | Then mark it `completed` with the one-line reason and re-print the block. Quick drops ceremony, never steps. A step that disappears with nothing written is a silent drop. |
| "There is no to-do tool in this session, so there is no ledger" | There is one. Print it in chat and re-print it at every boundary. Quick keeps nothing on disk, so the printed block is the only record the ledger has. |
| "Quick mode, so skip the ship gate" | The ship gate is always-on in every mode. If there is nothing to run, write the `⏭ skipped` row with the reason. That costs one line. |
| "This diff looks small, I'll just use the merged reviewer and save a round" | Not your call to make quietly. The five-agent panel runs by default because it finds more, measured rather than argued: on one real sprint diff it returned 29 findings and 4 Critical where the merged reviewer returned 16 and 1. The merged reviewer stays available at that lower cost, but only on a request you name out loud, "use the merged reviewer" or "single reviewer round", never as a substitution the parent reaches for on its own reading of a diff's size. |
| "It's a typo, I'll just edit the file myself" | The no-parent-authored-diff law binds in quick mode too, with no size threshold. Dispatch it. |
| "Quick mode means one agent, so no splitting" | Splitting is the first move, and the waves it falls out into dispatch in parallel up to the concurrent-wave budget. One agent is where a genuinely atomic change lands, not where you start. |
| "This one is too big, too spread out, or too sensitive for quick mode" | None of those route. Quick has no non-trigger list, and full mode runs only when the user asks for it by name. Reading a diff's shape as an implied request is the auto-promotion the user ruled out. |
| "This needs a real root-cause investigation, so it belongs in full mode" | Phase 3b runs here, in full. Quick owns debug asks, and the hunt is `../hackify/references/debug-when-stuck.md` read whole, circuit breaker included. A hard bug is not a promotion request. |
| "Two fixes missed, the third one will land it" | That is the trigger, not a reason to skip it. Stop guessing and open the hunt. After three failed hypotheses, stop again and surface to the user rather than trying fix #4. |
| "The re-scan was clean, done" | Only if the diff has not changed since that scan. Fixes applied after a scan were never reviewed. |
| "This task is getting bigger than I thought, let me silently switch to full mode for the user" | Quick mode never auto-promotes. The user explicitly opted into quick mode. Stay in quick mode until the user says "switch to full" or one of the documented promotion phrases. |

## One-line summary

Clarify-if-ambiguous + goal anchor → implement (parallel implementers under both dispatch budgets, one file-disjoint allowlist each) → verify fresh (triad + both scouts + ship gate) → five-agent panel, refute, then one address-all fix pass → touched-scope cleanup + plain-language update log, carried on one published page. Stays in quick mode until the user explicitly promotes to full hackify.
