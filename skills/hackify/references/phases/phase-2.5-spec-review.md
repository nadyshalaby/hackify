# Phase 2.5, Spec self-review (1 reviewer, mandatory)

Loaded by `SKILL.md` when this phase opens. The phase's entry conditions, hard gates and exit artifact are stated in `SKILL.md`; this file is the protocol.

**Goal.** Two jobs on one read. Catch inconsistent or conflicting logic in the work-doc *before* code is written, cheap on paper and expensive after 200 LOC against a flawed spec. And do the **contention analysis** Phase 3 dispatches on: name every serial resource the backlog touches, re-test each one for whether it is really exclusive, and extract every contended write into one solo foundation wave.

### Phase 2.5 is where contention gets found

Contention is invisible in a plan. A plan describes a bounded context and says nothing about the migration counter, because the plan speaks the domain's vocabulary and the contention lives in the build's. So this phase is the only place before dispatch where somebody asks what each task needs *beyond* its own files, and the answer decides the whole shape of Phase 3. Full technique: [../contention-dispatch.md](../contention-dispatch.md), which is canonical for the partition test and for the three classes of serial resource.

**The contention lens is unconditional.** The reviewer cannot see which mode dispatched it, so the exclusivity re-test and the foundation-wave extraction run on every work-doc, not only on the wide ones. Both are cheap and both are correct every time. Gating them on something the agent cannot observe is how a hard bound nobody re-tested survives into the partition.

**The size of the answer, not the running of the check, is what scales.** A backlog with no contended write writes `None.` under the `## Serial resources` heading and gets no foundation wave, and the wave plan says so in words rather than going quiet. That is the whole of what "it scales down to a two-file change" means here.

**First line of this turn, print the completion sentinel.** Sign-off just landed, so this is the first turn where a finish line can be stated and the first where the native tool is not blocked by plan mode. Emit one fenced `/goal <condition>` line (≤500 chars) naming the archived work-doc plus the green triad and the ship-gate rows, so an evaluator outside this conversation can rule on "done" instead of you. **You print it; only the user can set it**, so never claim a goal is active, never propose one from a subagent, never wait on the answer, and never soften the condition later to make it pass. Shape, the per-mode wording, and who wins when the sentinel and the iteration driver disagree: [references/orchestration.md](../orchestration.md).

**Ledger, at phase open.** Right after the sentinel, set `Phase 2.5. Spec review (1 reviewer, patch the doc)` to in-progress in the work-doc's `## 0. Phase ledger` block, then re-print the whole ledger block after that edit is saved. Frontmatter `status` stays `planning` through this phase, so that edit moves the marks alone. Never open it while `Phase 2. Plan + Gate` is still open. Contract: [../phase-ledger.md](../phase-ledger.md).

1. **Dispatch exactly 1 reviewer, `hackify:spec-reviewer`, in ONE message.** Dispatch it by registered agent type, passing only its INPUTS (absolute work-doc path, slug, wave-size target, project root, user-global rules path, concurrent-wave target, plugin root). Do not open the template to paste it. **The plugin root is the absolute filesystem path to the installed hackify plugin**, the directory holding `rules/` and `skills/`, and it anchors every REQUIRED READING path the template opens, so it never takes `none`: derive it from a path you ALREADY HOLD, either the absolute path carried in any always-on rule injection you received this session or your own skill's base directory, never by searching the filesystem. It carries three lenses over one read of the doc, because the planning lens and the rules lens were each a separate agent whose read set was a strict subset of this one's:
   - *Consistency + goal drift.* Read work-doc end-to-end. Find Q&A↔DoD↔Approach↔Sprint Backlog contradictions. Flag tasks not covered by any DoD bullet, DoD bullets not covered by any task, Q&A answers contradicting the Approach. **Drift-check:** trace every Sprint Backlog task + DoD bullet to the Primary Goal & Guardrails anchor, a task serving no In-Scope bullet → **drift (Important)**; one violating a Guardrail or Non-Goal → **Critical** (canonical wording: [references/goal-anchor.md](../goal-anchor.md)).
   - *Execution plan, which is also the contention analysis.* Build a dependency graph from the per-task file lists it extracted on that same read. Emit the topological wave plan as a `## Proposed wave plan` section, one line per wave, one dispatched implementer each, tasks in run order, each line naming the implementer type that wave takes. The LAST stage is the TESTING STAGE, authoring the tests for everything the earlier waves landed, so a plan whose last line is a module track has dropped a stage rather than finished early. **It is not automatically solo.** `sibling_tracks` is `none` on a foundation wave, an assembly wave, a testing stage that runs as one wave and a single-track round. **A testing stage that SPLITS is not on that list**: it splits into concurrent testing waves under the same partition test as every other stage, counted by the production surface it must cover rather than by the one backlog task carrying it, and each of those waves is handed the OTHER testing waves' IDs. Flag tasks sharing a file (breaks task-to-file attribution), missing prerequisites, ordering bugs (consuming a helper before its task), tasks too coarse to be 5-30 min. Three further things come out of this lens and go into the report:
     - **Name every serial resource, then re-test it.** Three kinds: any shared file two or more tasks write; any generated sequence whose next value is computed from what already exists (migration filenames numbered off a journal's length are the standing example); and any exclusive external resource such as a single test database. Each row carries its kind and the task IDs holding it, then a verdict of **genuinely exclusive** or merely **conventionally serial**, and for a conventional one the per-track isolation that lifts it. One test database reads as a hard bound because two integration runs truncate each other's tables mid-run, yet one fresh database per track lifts it entirely, and that single re-test took a real build's partition from four wide to nine. A row with no verdict is unfinished, not cautious. It all lands in a `## Serial resources` table.
     - **Mark which waves are concurrency candidates.** Apply all three conditions of the partition test to its own plan and close each wave line with `[concurrency candidate]` or `[serial: <the condition that fails>]`. **You MARK and the parent DECIDES**: the parent applies the same test itself at dispatch, so a wrong mark cannot start a bad concurrent run on its own.
     - **Extract every contended write into one solo foundation wave.** Every file two or more tasks write goes there and lands at once. That wave writes no business logic, because its real output is permission for everything else to run in parallel, which is why it goes first and alone. Wave 1 is the foundation wave whenever the backlog holds a contended write, and the wave plan says so on the line.
   - *Architectural / cross-cutting risk.* Match plan against project code-quality rules, if a `CLAUDE.md` is at workspace or project root, honor it; otherwise apply `rules/code-quality.md`. Flag anything that would force a lint suppression, `!`, inline type, bare `Error` throw, or layering violation. Also flag plan-time performance risk: a plan item that would bake in a `rules/performance.md` Critical before code exists, an N+1-shaped task, unbounded fan-out, a list endpoint with no pagination.
   - **Its report leads with the wave plan and then the serial resources**, both of them enumerations that sit outside the word budget, so a truncated report still carries the two things Phase 3 consumes.

**The letter C is retired, not reassigned, and so are A and B.** Phase 2.5 has no lettered reviewers left, so a work-doc or transcript naming "Reviewer A", "Reviewer B" or "Reviewer C" always means one of the three lenses the single reviewer now carries, never a separate dispatch. A future spec lens takes the next free letter. Phase 5 keeps its own lettered reviewers, a different panel in a different phase.
2. **Aggregate findings.** Critical (plan bug forcing rework) / Important (fixable gap) / Minor (nit).
3. **Patch the work-doc.** Apply Critical + Important in place; record Minor in Retrospective.
4. **Write the wave plan and the serial resources into the work-doc** under Approach, marks included, so Phase 3 reads them off disk rather than out of a scrolled-away report. A resource left without an exclusivity verdict is a finding to fix here, not something for the parent to guess at dispatch.
5. **Re-gate ONLY if user's signed-off invariants changed** (Critical finding widened scope). Else straight to Phase 3.

Template: `references/parallel-agents/phase-2.5-spec-reviewer.md` (subdir index: `references/parallel-agents/README.md`). **Hard rule:** Phase 2.5 is non-skippable, even for small docs, a "small" plan can hide a contradictory Q&A pair. Cap the report at ≤900 words, the sum of the three lenses it carries; its wave plan and its serial-resources table are enumerations and sit outside that budget.

**Ledger, at phase exit.** The reviewer report is aggregated and every Critical + Important finding is patched into the doc first, then one line of reflection (what changed, did it pass, what is next), then tick `Phase 2.5. Spec review` and open `Phase 3. Implement (all waves committed)` in the work-doc's section 0, saved before the re-print. A finding class that genuinely does not apply is recorded with a one-line reason, never dropped in silence.
